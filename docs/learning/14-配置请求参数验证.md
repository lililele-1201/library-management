# 第 14 节：配置请求参数验证

## 一、本节目标

这一节把前两节定义的 DTO 校验规则接入 NestJS 的真实请求流程。

完成后需要理解：

1. DTO 只负责定义规则，`ValidationPipe` 负责在请求到达 Controller 前执行规则。
2. `whitelist`、`forbidNonWhitelisted` 和 `transform` 分别解决什么问题。
3. 为什么全局管道只需要配置一次。

本节不会实现任何图书 CRUD 接口。

## 二、之前为什么只能直接测试 DTO

第 12、13 节已经写了：

```ts
export class CreateBookDto {
  @IsString()
  @IsNotEmpty()
  title: string;
}
```

这些装饰器只是保存了验证规则。没有管道时，HTTP 请求不会自动执行这些规则。

```text
没有 ValidationPipe：
HTTP 请求体 -> Controller

启用 ValidationPipe：
HTTP 请求体 -> ValidationPipe -> DTO 校验 -> Controller
```

所以 `ValidationPipe` 可以理解为请求进入 Controller 前的“检查站”。

## 三、先写失败测试

本节增加了一个只存在于测试文件中的示例 Controller 和 DTO，用来隔离验证管道的行为。

它测试三个场景：

1. `title` 传入数字时应返回 `400 Bad Request`。
2. 请求体包含 DTO 没有声明的字段时应返回 `400 Bad Request`。
3. 路径中的 `"42"` 应转换成数字 `42`。

未配置管道时，实际结果是：

```text
非法 title         -> 201，而不是 400
多余字段            -> 201，而不是 400
路径参数 42         -> string，而不是 number
```

这证明 DTO 不会自己拦截请求。

## 四、全局配置

文件：`backend/src/main.ts`

```ts
import { ValidationPipe } from '@nestjs/common';
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module.js';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  app.useGlobalPipes(
    new ValidationPipe({
      whitelist: true,
      forbidNonWhitelisted: true,
      transform: true,
    }),
  );
  await app.listen(process.env.PORT ?? 3000);
}
await bootstrap();
```

`app.useGlobalPipes()` 表示把管道应用到整个 Nest 应用。后续新增的所有 Controller 都会经过它，不需要每个接口重复配置。

## 五、三个配置项

### 1. whitelist: true

只允许 DTO 中声明过并带有验证装饰器的字段。

例如 DTO 只声明了 `title`：

```json
{
  "title": "NestJS 入门",
  "extra": "多余字段"
}
```

`extra` 不在 DTO 白名单中。

如果只开启 `whitelist`，Nest 会把 `extra` 删除后继续处理请求。

### 2. forbidNonWhitelisted: true

发现白名单以外的字段时，直接拒绝请求并返回 `400`，而不是悄悄删除。

```text
whitelist: true
  -> 识别并移除多余字段

whitelist: true + forbidNonWhitelisted: true
  -> 识别多余字段并返回 400
```

本项目选择直接拒绝，让客户端能立刻发现字段写错。

### 3. transform: true

HTTP 路径参数和查询参数最初都是字符串。

例如浏览器访问：

```text
/books/42
```

原始的 `42` 是字符串。Controller 参数声明为 `number` 时，`transform: true` 可以根据类型信息将它转换成数字。

```ts
findOne(@Param('id') id: number) {
  return typeof id; // number
}
```

转换不等于所有输入都一定合法。后续仍可以配合 DTO 或专门的参数管道限制具体格式。

## 六、一次请求如何经过校验

以后新增图书接口接收 `CreateBookDto` 时，调用链会是：

```text
客户端发送 JSON
  -> Nest 收到 HTTP 请求
  -> 全局 ValidationPipe
  -> class-transformer 转成 DTO 实例
  -> class-validator 执行装饰器规则
  -> 校验失败：Nest 返回 400
  -> 校验成功：进入 Controller
```

例如：

```json
{
  "title": 123,
  "author": "示例作者"
}
```

`title` 违反 `@IsString()`，因此请求会在进入 Controller 前被拒绝。

## 七、为什么测试里也配置了一遍管道

端到端测试通过下面的代码创建独立的 Nest 测试应用：

```ts
moduleFixture.createNestApplication();
```

这个测试应用不会执行正式入口文件 `main.ts`，因此也不会自动执行其中的 `useGlobalPipes()`。

测试中要配置同样的管道：

```ts
app.useGlobalPipes(
  new ValidationPipe({
    whitelist: true,
    forbidNonWhitelisted: true,
    transform: true,
  }),
);
```

这样测试的请求处理规则才与正式应用一致。

## 十二、常见误区

### 1. 认为 DTO 装饰器会自动运行

DTO 只是规则说明。必须通过 `ValidationPipe` 才能在 Nest HTTP 请求中自动执行。

### 2. 混淆 whitelist 与 forbidNonWhitelisted

`whitelist` 负责识别允许的字段；`forbidNonWhitelisted` 让多余字段直接触发错误。

### 3. 认为 TypeScript 类型能验证 HTTP 数据

TypeScript 类型在编译后会消失。运行时校验依靠 DTO 装饰器和 `ValidationPipe`。

### 4. 认为 transform 会修改数据库

`transform` 只转换请求数据的运行时类型，与数据库无关。

### 5. 在每个 Controller 重复配置

本项目使用全局管道，只需要在应用启动时配置一次。

## 十三、本节验收标准

1. `main.ts` 注册全局 `ValidationPipe`。
2. 开启 `whitelist`、`forbidNonWhitelisted` 和 `transform`。
3. 字段类型错误时，测试接口返回 `400`。
4. 请求体包含多余字段时，测试接口返回 `400`。
5. 数字路径参数可以转换成 `number`。
6. 全部单元测试、端到端测试、lint 和构建通过。
7. 没有提前实现图书 CRUD。

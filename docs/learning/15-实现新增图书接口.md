# 第 15 节：测试驱动实现新增图书接口

## 一、本节目标

这一节只实现一个接口：

```text
POST /api/books
```

它负责接收图书数据、通过 DTO 校验、写入 SQLite，并返回保存后的图书。

本节需要理解：

1. Controller、Service 和 Repository 在新增流程中分别负责什么。
2. `Repository.create()` 和 `Repository.save()` 的区别。
3. Nest 为什么默认给 `@Post()` 返回 `201 Created`。
4. 如何用测试 SQLite 验证数据真的写入数据库。

本节不实现列表、详情、修改、删除，也不处理 ISBN 重复错误。

## 二、先写失败测试

按照测试驱动开发的顺序，本节先增加测试，再写实现。

最初运行聚焦测试时，结果是：

```text
controller.create is not a function
service.create is not a function
```

这两个失败说明测试确实发现了缺少的功能，而不是没有执行到关键代码。

测试分为三层：

```text
Controller 单元测试
  -> 是否把 DTO 交给 Service

Service 单元测试
  -> 是否创建 Entity 并调用 Repository.save

HTTP 端到端测试
  -> 是否返回 201 并真正写入测试 SQLite
```

## 三、设置全局 API 前缀

文件：`backend/src/main.ts`

```ts
const app = await NestFactory.create(AppModule);
app.setGlobalPrefix('api');
```

`BooksController` 自己的路径是 `books`，全局前缀是 `api`，所以组合后的正式路径是：

```text
api + books = /api/books
```

它们不是字符串手动拼接，而是 Nest 根据全局前缀和 Controller 路径自动组合。

## 四、Controller 接收请求

文件：`backend/src/books/books.controller.ts`

```ts
import { Body, Controller, Post } from '@nestjs/common';
import { Book } from './book.entity.js';
import { BooksService } from './books.service.js';
import { CreateBookDto } from './dto/create-book.dto.js';

@Controller('books')
export class BooksController {
  constructor(private readonly booksService: BooksService) {}

  @Post()
  create(@Body() createBookDto: CreateBookDto): Promise<Book> {
    return this.booksService.create(createBookDto);
  }
}
```

### 1. 注入 BooksService

```ts
constructor(private readonly booksService: BooksService) {}
```

`BooksModule` 已经把 `BooksService` 注册在 `providers` 中，所以 Nest 会创建 Service，并通过构造函数交给 Controller。

### 2. @Post()

```ts
@Post()
```

它表示下面的 `create()` 方法处理 HTTP POST 请求。

因为 Controller 的前缀是 `books`，应用的全局前缀是 `api`，最终接口是：

```text
POST /api/books
```

Nest 对成功的 `@Post()` 默认返回 `201 Created`，所以这里不需要手动设置状态码。

### 3. @Body()

```ts
@Body() createBookDto: CreateBookDto
```

`@Body()` 读取请求中的 JSON body。

因为参数类型是 `CreateBookDto`，上一节配置的全局 `ValidationPipe` 会在进入方法前执行 DTO 校验。

### 4. Controller 不直接操作数据库

Controller 只接收 HTTP 数据并调用 Service：

```ts
return this.booksService.create(createBookDto);
```

数据库操作交给 Service，避免把 HTTP 处理和业务步骤混在一起。

## 五、Service 保存图书

文件：`backend/src/books/books.service.ts`

```ts
create(createBookDto: CreateBookDto): Promise<Book> {
  const book = this.bookRepository.create({
    ...createBookDto,
    isbn: createBookDto.isbn ?? null,
    publishedYear: createBookDto.publishedYear ?? null,
  });

  return this.bookRepository.save(book);
}
```

### 1. Repository.create()

```ts
const book = this.bookRepository.create(...);
```

它根据传入数据创建一个 `Book` Entity 对象，但此时还没有写入数据库。

```text
Repository.create()
  -> 得到内存中的 Book 对象
  -> 数据库中还没有这条记录
```

### 2. 为什么把缺少的可选字段改成 null

DTO 允许不传 `isbn` 和 `publishedYear`。Entity 中这两个字段使用 `null` 表示数据库空值：

```ts
isbn: createBookDto.isbn ?? null,
publishedYear: createBookDto.publishedYear ?? null,
```

`??` 的意思是：左边是 `undefined` 或 `null` 时，使用右边的值。

因此：

```text
传入 ISBN       -> 使用传入值
不传 ISBN       -> 保存 null
```

### 3. Repository.save()

```ts
return this.bookRepository.save(book);
```

`save()` 才会真正执行数据库写入。

新增成功后，TypeORM 会把数据库生成的内容放回 Book 对象，例如：

```text
id          -> SQLite 自增生成
createdAt   -> TypeORM 自动生成
updatedAt   -> TypeORM 自动生成
```

`save()` 返回 Promise，所以 Service 的返回类型是：

```ts
Promise<Book>
```

## 六、完整调用链

客户端发送：

```json
{
  "title": "NestJS 入门",
  "author": "示例作者",
  "isbn": "978-7-0000-0000-1",
  "publishedYear": 2026
}
```

服务端调用链：

```text
POST /api/books
  -> 全局 ValidationPipe
  -> CreateBookDto 校验
  -> BooksController.create()
  -> BooksService.create()
  -> Repository<Book>.create()
  -> Repository<Book>.save()
  -> SQLite INSERT
  -> 返回保存后的 Book
  -> HTTP 201 Created
```

成功响应大致是：

```json
{
  "id": 1,
  "title": "NestJS 入门",
  "author": "示例作者",
  "isbn": "978-7-0000-0000-1",
  "publishedYear": 2026,
  "createdAt": "2026-09-17T00:00:00.000Z",
  "updatedAt": "2026-09-17T00:00:00.000Z"
}
```

## 七、三种测试各自验证什么

### 1. Controller 单元测试

用假的 `BooksService` 替代真实 Service，确认 Controller 把 DTO 原样交给它。

```text
DTO -> Controller -> 模拟 BooksService.create()
```

这个测试不启动 HTTP，也不连接数据库。

### 2. Service 单元测试

用假的 Repository 替代真实 TypeORM Repository，确认：

1. 调用了 `Repository.create()`。
2. 可选字段缺失时变为 `null`。
3. 调用了 `Repository.save()`。
4. 返回保存后的 Book。

这个测试不连接真实数据库。

### 3. HTTP 端到端测试

端到端测试启动 Nest 测试应用，并使用 SQLite 内存数据库：

```ts
database: ':memory:'
```

它只在测试进程的内存中存在，测试结束后自动消失，不会污染 `backend/data/library.sqlite`。

测试不仅检查响应，还使用 Repository 再查一次数据库，确认记录确实存在。

## 八、合法和非法请求

合法请求：

```json
{
  "title": "NestJS 入门",
  "author": "示例作者"
}
```

预期返回 `201`。

非法请求：

```json
{
  "title": ""
}
```

它缺少 `author`，而且 `title` 为空。全局 `ValidationPipe` 会在 Controller 运行前返回 `400`，数据库记录数保持为 `0`。

## 十二、常见误区

### 1. 认为 Repository.create() 已经写入数据库

`create()` 只创建 Entity 对象，`save()` 才执行数据库写入。

### 2. 在 Controller 直接调用 Repository

本项目让 Controller 处理 HTTP，让 Service 组织业务步骤，让 Repository 操作数据库。

### 3. 手动生成 id 和时间

`id`、`createdAt`、`updatedAt` 已由 Entity 装饰器和 TypeORM 管理，不应该放进新增 DTO。

### 4. 手动返回 201

Nest 的 `@Post()` 成功时默认就是 `201`，这里不需要额外配置。

### 5. 使用正式数据库做自动化测试

本节的端到端测试使用 SQLite 内存数据库，避免测试数据污染本地正式数据库文件。

### 6. 提前实现其他接口

列表属于第 16 节，详情属于第 17 节，修改和删除属于后续节点。本节只实现 POST。

## 十三、本节验收标准

1. 正式应用启用 `/api` 全局前缀。
2. `POST /api/books` 接收 `CreateBookDto`。
3. Controller 只把新增任务交给 Service。
4. Service 使用 Repository 创建并保存 Book。
5. 成功响应状态为 `201`。
6. 响应包含自增 ID 和时间字段。
7. 端到端测试确认 SQLite 中存在记录。
8. 非法数据返回 `400`，不会写入数据库。
9. 没有实现列表、详情、修改、删除或 ISBN 冲突处理。
